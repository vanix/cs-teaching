網路服務架構互動教學

主從式架構 (Client-Server) vs. 點對點架構 (P2P)

情境 1：Instagram 發照片與看動態

主從式架構 (Client-Server Architecture)

上方為中央伺服器 (Server)，下方為使用者 (Clients)。發文必須先傳至 Server，粉絲才能從 Server 接收貼文。

Client-Server HTTP/HTTPS 傳輸日誌

> 系統準備就緒，請點擊「發布 IG 新貼文」開始測試...

集中管理 (Centralized)

所有請求（發文、按讚、讀取動態）都必須經過中央 Server 驗證處理，權限集中。

單點故障 (SPOF)

如果頂端的中央 Server 故障或網路斷線，全世界所有 Client 均無法使用服務。

伺服器負擔大

幾百萬人同時刷貼文時，Server 必須同時傳送幾百萬份拷貝，頻寬與設備成本極高。

情境 2：AirDrop 近距離無線直連

點對點架構 (P2P) —— 面對面傳照片

完全不需要網際網路或中央伺服器。設備間透過 BLE 搜尋，並以 Wi-Fi Direct 進行雙向點對點直連。

Bluetooth / Wi-Fi Direct (P2P) 傳輸日誌

> 點擊「1. 廣播搜尋」或「2. 單傳/群發照片」發射高亮光束...

不需要伺服器與外網

即使在山頂、地下室或完全無基地台訊號的地方，兩台手機依然可以互相對傳檔案。

傳輸快速與高隱私

檔案直接從 A 點點對點飛向 B 點，不經過任何雲端 Server 儲存，保護個人隱私。

距離物理限制

受限於無線電波距離（通常在 10 公尺內），且雙方必須同時啟用相同的 P2P 協定。

情境 3：BT 種子檔案碎片互傳 (BitTorrent)

點對點架構 (P2P) —— 人人為我，我為人人

大檔案被切割成多個彩色區塊（Pieces）。大家一邊下載，一邊把手頭有的區塊分享給其他同學。

BitTorrent Piece Exchange ( Swarm 檔案區塊交換日誌 )

> 初始狀態：Peer A 為做種者 (Seeder 100%)，擁有一切區塊。

越多人下載，速度反而越快

不同於 Client-Server 人多會塞車，BT 中每個新下載者同時也是上傳者，網路總上傳頻寬爆發成長！

檔案碎片化 (Chunk Sharing)

檔案切成獨立碎片，不用等 100% 下載完，只要拿到 25% 就可以立刻上傳分享給別人。

依賴做種者 (Seeder)

如果擁有 100% 完整檔案的做種者全部離線且區塊不齊全，下載就會停滯（俗稱死種）。

主從式 (Client-Server) vs 點對點 (P2P) 完整對比表

專為教學與電子白板講解設計的大字對照表。

比較項目 主從式架構 (Client-Server) 點對點架構 (P2P)
代表性應用場景 Instagram、網頁瀏覽、網路銀行、原神、YouTube 影片串流 AirDrop 傳照片、BT 種子下載、區塊鏈 (Bitcoin)、Skype 早期語音
中央伺服器需求 極度依賴 大型雲端伺服器機房 完全不需要 或僅需少量配對機房
用戶暴增時影響 伺服器極易塞車、延遲卡頓，甚至坍塌 (炸服) 下載與上傳節點同步變多，總頻寬反而飆升
單點故障 (SPOF) 風險極高 (中央 Server 掛掉時全體癱瘓) 風險極低 (個別電腦離線不影響其他電腦傳輸)
資料管理與安全 容易管理 (集中於 Server，易於統一驗證與備份) 分散於各用戶電腦，需額外防範惡意病毒與作弊
營運與頻寬成本 機房電費與專線頻寬費用極為昂貴 硬體與頻寬成本極低 (借用使用者的設備)
